# V3 Architecture Audit — docs/ARCHITECTURE_V3.md

**Date:** 2026-07-05

Full-scale architectural audit of `docs/ARCHITECTURE_V3.md`. Method: four parallel adversarial scouts (A: problem definition & root-cause fit, §1–6; B: UX/dedup/validators/provenance/ranking/missing-problem, §7–10, 13–14; C: codebase alignment/data model/Master CV semantics/tailoring safety, §11–12, 15–16; D: eval harness/red-team/simplicity/plan, §17–20), followed by an in-place verification pass ([auditor] notes; corrected values are authoritative), synthesized here. Findings files under `research/v3_audit/`. Evidence: the working tree at `v2/master-cv`, the live `jobpilot.db` (read-only, 2026-07-05), and predecessor docs read from unmerged branches.

> **Root cause.** ARCHITECTURE_V3's central reframe — one reviewable Project Story per confirmed entity, claims demoted to inventory — is correct and solves the review-explosion root problem. But the doc systematically mistakes *statements* for *mechanisms*: it describes the resume_ready render gate as present-tense behavior of `build_snapshot_content` when no such gate exists in code (the function filters only approved-claim + confirmed-entity, `app/domain/master_cv_snapshot.py:70-105`, and `tests/test_claims_routes.py:249-279` proves a Result-less claim renders a docx today); it has no human `approved` status distinct from machine-assigned `resume_ready`; it specifies enforcement as a disabled UI button and prompt instructions while §6 retires the one server-side integrity gate that exists (`FlaggedClaimApprovalError`, `app/services/claim_review.py:47-58`) with no replacement; and its "compose and elevate" relaxation moves the evidenced/invented boundary into unverifiable LLM self-policing. Net: the right abstraction, keyed to a gate that is currently enforced zero times, wired so that trust migrates from mechanical checks to model judgment exactly where the live corpus (148 pending claims, 130 flagged, 15 confirmed entities) needs it most.

**Settled corpus facts** (live DB, [auditor]-verified): 15 confirmed entities — 12 with pending claims, 3 claim-less (`Jobpilot` 116 chunks / 0 claims / 7 `extraction_failure` rows; `DS4635` 10 chunks / 0 claims; `Paper recommender system` 0 evidence). 148 pending claims, 1 approved (claim 373), 1 rejected. Flags: `problem_missing` ×111, `action_tool_not_in_text` ×37, `result_problem_coupling` ×21, `action_names_no_tools` ×13, `duplicate_outcome_span` ×7 — 130/148 claims flagged. A cross-entity duplicate Result ("Top 3 out of 100+ teams") already exists under two entities (claims 472/513). The §3.4 render-time P-A-R gate does not exist in code today.

## 1. Actual Problem Space

**Verdict: directionally correct — it names the real hard problem (project discovery, evidence merging, problem-space definition, elicitation, readiness gating) — with four defects that matter architecturally** (Scout A §1):

- **(a) It redefines the product as the compiler.** CLAUDE.md defines Jobpilot as the full pipeline; the compiler is the hard upstream stage, not the product. This framing licenses ignoring downstream contracts — which S5 then does (matching and interview prep consume the same `master_cv_from_snapshot` bridge, `app/services/pipeline.py:129-132`, `app/services/interview_scan.py:141-142`, and S5 never mentions them).
- **(b) It omits the truthfulness invariant.** "Accurate" is too weak; resume.md (commit `43d217a`) states the actual bar: "no prose leaves the machine unless it traces to evidence a human approved." The hard problem includes verifiability under LLM composition — the exact property §3.1's relaxation trades against.
- **(c) It underweights the user's own thesis.** The end user is by thesis burned out; "minimal user effort" is the core mechanism, not polish. The definition should state a hard review budget (single sitting, minutes) as a constraint.
- **(d) It misses two load-bearing properties the live data proves:** elicitation is the **primary** manufacturing step, not a fallback — 111/148 pending claims carry `problem_missing`, and 4–5 of 12 claim-bearing entities cannot reach Problem+Result from evidence at all ([auditor: investment-decision-workflow-engine's pending queue is 8/0/1 but its one approved claim carries a one-line technical problem, so "cannot at all" overstates that one entity; the other four hold]); and incrementality/decision-preservation must be a stated requirement, not an inherited habit. Also missing: goal-conditioning — "resume-ready" is relative to target roles (§3.8 knows this; §1 doesn't).

**Improved definition (delta):** an evidence-to-career-story compiler producing a small set of *verifiably true*, high-leverage, project-level stories, conditioned on target roles, within a review budget of minutes; every story sentence traces to owned evidence or a typed attestation; elicitation via fewest highest-value questions is the primary path for evidence-sparse projects; incremental, idempotent, never overrides a human decision; its approved output is the **only** input to every downstream consumer.

## 2. Architecture Summary

**Central object:** `project_stories`, one row per confirmed entity (`experience_id` unique, §2); claims demoted to inventory (§0); evidence/claims tables untouched. **Pipeline:** V2 stages unchanged through PAR validation, then ★ one DEEP synthesis call per entity → ★ story review ("~12 cards") → Master CV = snapshot of `resume_ready` stories → tailoring/outreach/prep "draw from approved stories." **Persisted:** everything, including LLM drafts — the doc marks nothing ephemeral and never justifies keeping both LLM stages (claim extraction at BULK cost feeding inventory synthesis could arguably derive from chunks directly). Fifteen concrete commitments (table, status enum, one-DEEP-call + `synthesis_hash`, composition relaxation, gate "enforced three times," approve-cascade, `eval_stories`, retirements, S1–S6 order, no-data-loss migration) — Scout A §2 enumerates all.

**Ambiguities and silences (each a finding):**
1. **No `approved` story status** — §2's machine ends at `resume_ready`; §3.4 says synthesis assigns status; §4 says approval "becomes canonical." The render key may be machine-assigned. (Critical.)
2. `evidence_only` is never defined (appears in the §2 enum and §5's run report only); `needs_action` has no §3.6 elicitation question — an unreachable-by-review status.
3. Integrity flags at the story layer — 78 of 189 live flags (tool-not-in-text, coupling, no-tools, dup-span) have no stated disposition.
4. The Answer flow's terminal state — auto-approve after re-gate, or wait?
5. The `MasterCv` bridge (`master_cv_snapshot.py:126-151`) feeds matching, tailoring, and prep; S5 mentions only tailoring.
6. Whether tailoring may reach non-resume_ready inventory — §4's "never renders" is render-scoped only.
7. The legacy per-file extraction fallback (`claim_extraction.py:427-437`) — never mentioned, never retired.
8. Claim-less evidence-bearing entities (Jobpilot 116/0, DS4635 10/0) — does synthesis run on chunk-only input? "~12" vs 15 confirmed entities.
9. The composed `problem_space` exists on no claim — its post-approval provenance/audit story is implicit on the story row.
10. The doc's header cites `docs/REVIEW_LAYER_AUDIT.md` as its superseded predecessor, but that file exists only on branch `docs/review-layer-audit` (commit `2375ba9`) — the pointer dangles on the branch V3 work would happen on.

## 4. Core Object Review

The correct core object is the **Approved Project Story** — one per real-world entity, evidence spans as immutable leaves, claims as never-user-facing intermediates. The doc **is** centered on it (§0, §2), claims are inventory by declaration, one-project-once holds structurally, and the user reviews stories in the primary flow. **Critical failure at the write path:** §4's Edit is "per-component drill-down (existing edit-attest flow)" — but that flow is per-*claim* machinery (`app/services/claim_review.py`; `ClaimEdits`, `app/domain/claims.py:~1012`), and a composed `problem_space` lives on the story row, on no claim. The specified mechanism (a) re-exposes the raw claims V3 promises the user never sees, and (b) **cannot edit the story's most important component** — editing the composed Problem requires story-component edit-attest machinery the doc hand-waves as "existing machinery." Specification hole at the core object's write path (Scout A §4; Scout C §12 HumanAttestation row: attestation refs are `claim:{id}:{field}`, `claims.py:998-1005`, and `plan_claim_edit` requires a pending claim, `claims.py:1017-1018` — §3.1's "existing machinery" claim is false as written).

## 5. Project Story Model Audit

- **Problem Space required?** Yes for resume-readiness, with honest downgrade (`needs_problem`). But `evidence_only`/`portfolio_inventory` semantics are undefined and nothing assigns one vs the other.
- **Actions coupled to the Problem?** **Half-coupled, decoupled where the live data needs coupling most** (Scout A §5): ranking is by `career_signal_score`, an independent axis; for the 4–5 live entities with no problem space, "remedied the Problem Space" is vacuous — actions are chosen by career signal alone for a plurality of real projects; and after a user attests a problem, §4 re-gates with "no LLM call" — actions are **never re-selected against the newly attested problem**. The P→A arrow is prompt guidance, not architecture.
- **Results tied to Actions?** **No — structurally absent.** §0 defines Results as "caused by those actions," but §3.3's shape has no action reference and §3.4's gate checks co-presence only. V2's weak `resolves` coupling (`par_validation.py:271`) is dropped without replacement; the 21 live `result_problem_coupling` flags have no story-level answer anywhere in the doc.
- **Missing Problem/Result → targeted question, never invented?** Yes (§3.1, §3.3, §3.6) — the doc's strongest material — with the caveat that "compose and elevate" moves the invented/composed boundary into LLM judgment with no deterministic backstop.
- **Low-value exclusion?** `exclude_low_value` is terminal and render-gated; tailoring-side exclusion unstated.

## 6. Resume-Ready Gate

The gate is explicit (§3.4: evidenced/attested Problem + ≥1 approved Action + evidenced/attested Result, same `experience_id`; "approved Actions" is undefined — actions carry no individual approval state). It is enforceable in code — as a pure domain gate, a **server-side 409** on approve, and a rewritten `build_snapshot_content` — but the doc promises only a *disabled UI approve control* while §6 retires the existing per-claim 409 gate. **"Enforced three times" is currently enforced zero times** (Scout A §6, Scout C): `build_snapshot_content` (`master_cv_snapshot.py:70-105`) filters claim `APPROVED` (line 80) + entity `CONFIRMED` (line 90) and nothing else; the predecessor render-time P-A-R bar was never implemented (resume.md: "designed but not yet enforced"). **Live counterexample:** entity 9 (`investment-decision-workflow-engine`) renders today via approved claim 373 — whose only Problem is a one-line technical bug ("streamlit run executed dashboard.py as a top-level script…") that fails §3.1's own "higher-level than a one-line bug" bar [auditor-corrected: claim 373 is problem-bearing; the render outcome stands]. Tailoring is gated only transitively — §3.4 names synthesis/review/render as enforcement sites, never tailoring; with no `approved` status, "approved stories" is undefined and tailoring may key to machine-assigned `resume_ready`. **Render-leak paths:** (1) today, all of them; (2) during migration, S4 (approve cascade) ships before S5 (render rewrite); (3) fallback entities have no stories; (4) worst — a synthesis draft passing the gate renders without any human seeing the card, one status-enum entry from fixed.

## 7. User Review UX

**The reframe is right and survives; the numbers, the drill-down, and the missing debug boundary do not** (Scout B §7).

- **Count:** 15 confirmed entities → **15 cards** (and 15 DEEP calls, not "~12" — §2 gives every confirmed entity a story row, including the 3 claim-less ones). Realistic surface: 7 cards plausibly ready without questions (MassDEP 20/3/7, Wellington 16/5/5, OneWorld 16/7/1, portfolio 12/4/7, Embue 11/3/6, Oasis 11/2/2, BoardGameGeek 11/7/5); 2 `needs_problem` (investment-decision-workflow-engine 8/0/1, Stock Market Simulation 5/0/2); 1 `needs_result` (Cooper.ai 3/3/0); 2 needing **both** (personal-knowledge-os 28/2/0 — its two "problems" are one-line pgvector/binary bugs failing §3.1's own bar; AI-Recovery-navigation 7/1/0, a `.gitignore` bug); 3 claim-less classifications. **Total ≈ 24–30 interactions — roughly 2× the doc's "~15," but still minutes. A real user would tolerate this.**
- **Never in normal review** (the doc gets the queue right): raw claim atoms, validator flag strings, fragment actions, `resolves` machinery, dedupe/drop logs, `#chars=` span refs.

**§3.7's cross-entity duplicate detection is unimplementable as written** (Scout B critical flaw): synthesis is one DEEP call per entity whose input contains exactly one entity — it structurally cannot "detect that two confirmed entities are the same project," and `duplicate_needs_merge` "naming the counterpart" cannot know the counterpart's name. **"Cross-project is unrepresentable" (§3.2) is false for container entities** — the portfolio proves blending is representable and happening. **The "no duplicate bullets in the final Master CV" guarantee is enforced nowhere:** §5's metrics count orphans and invented metrics, not duplicates; two resume_ready stories can each carry the same metric onto the CV — on the live corpus, they would.

## 9. Validator Strategy

Baseline (code-verified): `STRUCTURAL_CODES = {problem_not_specific, action_fragment}` (`par_validation.py:48`) + cross-boundary citations dropped pre-persistence; everything else is advisory flags, and `approve_claim` 409s on any flag (`claim_review.py:47-58`).

**Fatal failures at the story layer** (Scout B §9): cross-project results and invented metrics fail S1 validation — **but a failed story has no status**: §2's enum has no failed/quarantine value and §4's card list no place for it; fatal failures are log-only, invisible, exactly like today's `result.dropped`. One-word Problems and fragment Actions are structurally dropped at claim level but **S1's structural list (orphan refs, cross-entity refs, unsupported numbers) contains no artifact-pattern, specificity, or fragment check on *composed* prose**. Document-sized citations are checked nowhere (V2_AUDIT's ≤1,200-char citation-eligibility validator was never built; claim 374 cites a 1,417-char commit as Result evidence). Repairable→question routing is the doc's strongest part (missing P/R → exactly right).

**The 409 retirement is incoherent and a truthfulness regression:** §6 retires the per-claim 409 gate while §4 approves cited claims "over existing machinery" — on the live corpus **130/148 claims are flagged**, so either story approval throws `FlaggedClaimApprovalError` on nearly every story, or the gate is deleted and a claim carrying `action_tool_not_in_text` (an ungrounded tool that flows into skills/bullets) becomes approved with no attestation and no story-level recheck. The remaining **78 integrity flags** (tool-not-in-text ×37, coupling ×21, no-tools ×13, dup-span ×7) get no disposition: not on cards, not translated to questions, and visible verbatim one click deep in the drill-down. REVIEW_LAYER_AUDIT R2 had the right split — reclassify the absence family, **keep integrity flags blocking** — and V3 dropped the distinction.

## 10. Evidence and Provenance

Per-item audit (Scout B §10): source id/type/normalized text/project id — all exist. **Span offsets are a hack, not schema**: `source_ref` suffix `#chars=start-end` (`claims.py:871-890`), 633/761 live rows; commits and legacy rows have none; quote-level offsets were never built. **Quotes exist for Results only**: `outcome_quote` on `field='result'` (37 live); the 39 problem + 150 action links carry **zero quotes** — a P/A citation means "somewhere in this ≤1,200-char chunk," and V3 adds no quote requirement for composed-Problem `supporting_refs`. **No Technology evidence field** — §3.2's per-action `tools` have no link type, and the only tool-grounding check (`action_tool_not_in_text`) is being retired without replacement. `confidence` is decorative: no scale, no producer spec, no consumer.

Traceability: bullet→component and component→evidence are specified only via `orphan_component_count` over JSON blobs — one eval metric, no FK integrity. The number gate covers **Results only** — a composed Problem saying "used by ~160 professionals" is checked by nothing. Citation precision: Drive/README chunks are genuinely ≤1,200 chars (`MAX_CHUNK_CHARS`, `chunking.py:27`); commits are unbounded — 10 assigned commit chunks exceed 1,200 chars live (max 2,696); legacy whole-document rows up to 22.7KB still sit in `evidence`, citable, with no size validator. **Three cross-project leak vectors survive:** container entities (proven live), chunk misassignment (token-overlap heuristic, no review surface), and composed text leaking from the model's prior (refs existence-checked, never entailment-checked).

## 11. Current Codebase Alignment

**Already supports V3** (Scout C §11.1): the roster layer (proposer/assigner protocols, confirm/merge/rename API, migration `0010`) maps 1:1 onto "one story per confirmed entity"; extraction already lands everything `pending_review` with `extraction_hash` skip economics (`claim_extraction.py:457-462`) — exactly what `synthesis_hash` wants; attestation machinery; `verbatim_in` grounding plumbing and the cached-context batching pattern; `validation_runs` + `compute_slop_metrics` for `story_eval`; the state-machine/409 API conventions.

**Contradicts V3 / must be retired or rebuilt** (§11.2):

- **The legacy per-file fallback doesn't just survive — it auto-CONFIRMS entities.** `run_claim_extraction` falls back to per-file grouping (`claim_extraction.py:428-437`) and `upsert_experience` hard-codes `ExperienceStatus.CONFIRMED` (`db/claim_repository.py:127-128`): file-shaped, render-eligible, `PROFESSIONAL_EXPERIENCE`-sectioned entities with zero human roster review — directly contradicting §1's "human roster confirmation (V2, unchanged)."
- **An approved action-only claim renders today.** `render_claim_bullet` renders "the action alone" when Result is missing (`resume_context.py:90-99`); no completeness filter anywhere; `tests/test_claims_routes.py:249-279` seeds a `result_kind=MISSING` claim and asserts a successful docx — a test proving the behavior V3 forbids.
- **The docx render path bypasses both the snapshot and the confirmed-entity filter**: `render_master_cv_artifact` snapshots, then rebuilds context from *live* queries (`master_cv_render.py:68-72`); `build_resume_context` has no `ExperienceStatus` check — a discarded entity with approved claims still renders and the docx can diverge from its stamped version. V3 inherits this split enforcement unexamined.
- The claims queue UI, the flagged-409 path, and the Missing-Results queue are the retirement surface; the bar for "GitHub repo = resume-ready" today is one roster confirm + one approved action-only claim — no credible-P/R bar exists anywhere.

**Tests that give false confidence under V3** (§11.3): `tests/test_full_v2_loop.py:36-151` (asserts queue-length==claim-count, per-claim approve/attest/reject, bullet-per-claim tracing — every assertion encodes retired semantics; green paint on a retired pipeline); `tests/test_claims_routes.py` (asserts the 409 §6 removes, the retired queue, the forbidden incomplete-PAR render, the claim-shaped snapshot); `tests/test_claim_review.py` per-claim flows (its attestation-provenance test is the one worth porting, not deleting). **Migrations/services:** migration `0012`; the `content_json` shape change breaks fingerprint continuity (say so); `project_stories.experience_id` vs merged entities is unaddressed (nothing cleans a story whose entity becomes `merged`); redesign in dependency order: claim_review → snapshot builder + adapter → resume_context → render → api → web → pipeline → eval tool.

**JSON blobs break three things structurally**: per-component approval state (no component identity to transition — §4's component edit-attest has nothing to address); component-level provenance queries (refs buried in blobs, unindexable, dangle silently after merges); and **the golden set** — `golden_examples` (`evaluation.py:181-223`) exports labeled claim rows, and §4's cascade stamps approve-labels on claims the human never read, degrading "decisions are the V3 golden-set data" (CLAUDE.md) in exactly the release named after it. Workable compromise the doc forfeits: components may **only** cite `claim_ids` (claims stay the relational provenance/approval substrate; JSON purely presentational) — §3.2 explicitly allows bare evidence refs instead.

## 13. Ranking and Selection

**V3 has no real ranking model** (Scout B §13). §3.8 is ten unweighted adjectives with no algorithm, weights, owner, scale, or tests. The only concrete fields — `career_signal_score`, `result_strength_score` — are emitted by the same LLM inside the synthesis JSON: **the model ranks its own output**, unvalidated, non-deterministic; S2's heuristic fallback selects "best existing claims" with "best" undefined. This is an unambiguous regression from REVIEW_LAYER_AUDIT's deterministic leverage score (verified 4 / attested 3 / problem-bearing action 2 / bare action 1, plus tie-breakers, `domain/review_ranking.py`) — testable, defined, sufficient at n=15. Exclusion candidates are not ranked at all: `exclude_low_value` has no criterion or recommendation; spotting low-value projects stays on the user. Because the scores have no spec, S6's ≤15-interaction exit criterion cannot be tested against the ranking that's supposed to achieve it.

## 14. Missing Business Problem Handling

**The doc's best section** (Scout B §14): never fill a missing Problem; `needs_problem` + one targeted question; typed answers → `user_attestation` evidence with `problem_status=user_attested` over real machinery; the §0 worked example correctly marks unproven metrics, never fills them. [auditor: this restates *promised* enforcement — the render refusal does not exist in current code; §3.4's present tense is confirmed false today.]

**Where "compose and elevate" breaks (the attack):** README chunk → overwhelmingly problem-less claims (111/148 `problem_missing`) → synthesis "may compose and elevate." The stated guards: (a) `supporting_refs` required — checked only as *orphan-ref existence*; (b) "a problem the evidence cannot support is not written" — **an instruction to the same LLM doing the composing**. Nobody checks that refs entail the composed text; no verbatim requirement (explicitly relaxed), no entailment check, no quotes on problem refs (V2's problem links already carry none — verified live), and the §5 number gate covers metrics only. A README's aspirational framing ("democratizes recovery support…") can be elevated into a confident business problem, ref'd to the chunk it loosely paraphrases, and shown on the card labeled **[evidenced]** — the V1 "polished but unsupported" failure reborn at the Problem layer, with a UI label that actively overstates its support. There is no `tentative`/`inferred` middle state prompting confirmation, and no assignment rule distinguishing "ask the user" (`needs_problem`) from "don't bother" (`portfolio_inventory`) — the LLM picks among seven statuses with no criteria, and for the live corpus (personal-knowledge-os, AI-Recovery-navigation with one-line technical "problems") the answer changes both the review surface and the CV.

## 15. Master CV Semantics

Defined as structured approved data **in intent** (§1, §4, §2's provenance chain); **in schema** the canonical object is a status value on a mutable draft row (§12's ApprovedProjectStory hole). **Bullets are no longer downstream renderings — a quiet regression from V2**: today bullets are derived deterministically at render time from approved claim fields (`render_claim_bullet` — "no rewriting, no invention"); V3 persists LLM-composed `bullets_json` in the canonical row, approved wholesale, selected directly by tailoring. V2's render layer was mechanically incapable of rewording; V3's is prompt-constrained only. "Different resumes from the same stories" is implied but has no landing zone (artifact kinds, per-job render path, selection persistence — all unspecified).

**Three paths where generated prose becomes canonical** (Scout C §15, increasing severity): (1) the composed Problem — after approval it lives in `project_stories.problem_space` as render canon, never faced the PAR problem gate or `verbatim_in`, and post-approval is validated by **nothing**; §2's guarantee "every rendered sentence still walks back to a file the user owns or a statement the user typed" is **false** for it. (2) The §4 approval cascade — a story-level judgment converts to claim-level canon; the human approved a summary *of* the claims, not the claims; flagged claims inherit approval; cascade approvals enter the golden set as human verdicts they are not. (3) Persisted bullets feeding tailoring — generated text grounding further generation, two hops from evidence. The one genuinely sound containment choice — composed story text never enters `evidence` (only user-typed answers do) — deserves to be stated as an invariant; the doc leaves it implicit.

## 19. Simplicity / Overengineering

**The minimum viable V3** (Scout D §19) — the problem is *148 micro-decisions nobody will make, on an inventory that can't say which projects are resume-worthy*; the MVP that solves it is: (1) Phase-0 closure (delete the fallback's CONFIRMED minting; split integrity/absence flags); (2) a pure readiness computation over the existing claims ledger (~50 lines, no LLM, no migration); (3) questions derived from the fixed §3.6 taxonomy; (4) a project-card review endpoint (select claims, attest via existing `plan_claim_edit`, approve — one decision per entity); (5) the render-time P-A-R bar in `build_snapshot_content`. That is ~15 cards, no invented prose, **zero LLM spend, no new table**. The LLM synthesis layer — composed Problems, ranked actions, candidate bullets — is a quality upgrade *on top of* this, not the foundation. REVIEW_LAYER_AUDIT §5–6 already described this MVP; V3 supersedes it with a heavier design. The one genuine simplification V3 adds: retiring `shelved` (uncited claims simply stay inventory) — correct.

**V3's own overengineering:** ten statuses of which only four are lifecycle states — `needs_*` are **derived facts** (a scalar status cannot represent compound gaps); `needs_action` is near-unreachable; `evidence_only` vs `portfolio_inventory` is a distinction without behavioral difference (collapse); `exclude_low_value` duplicates roster `DISCARDED`; `duplicate_needs_merge` is a relation, not a state. **Verdict: 4 statuses + a readiness struct + a merge-prompt list.** Cut `confidence`/`career_signal_score`/`result_strength_score` (specced nowhere; the LLM will emit vibes-numbers) — reuse the deterministic 4/3/2/1 leverage score. **The heuristic synthesizer must select and gate, never author prose** — deterministic authoring of Problem paragraphs is template slop with an `evidenced` label, and with API credits exhausted it is what would run against live data first. `questions_json`: derive at read time, store only the answers (they're attestations — already a table). `bullets_json`: premature — render P/A/R directly first. `synthesis_hash`: justified, keep.

**Must be deleted (not deferred):** the per-file fallback's ability to mint CONFIRMED entities (`claim_extraction.py:427-437` + `upsert_experience`); the claims-queue-as-review-surface once story cards pass exit tests; `tests/test_roster_service.py:334`'s assertion that the fallback works (invert it). **Correctly deferred, keep deferring:** vector/embedding RAG, LLM judges, RL/self-improvement, broad Drive ingestion, multi-user assumptions, UI polish, elaborate scoring.

## 22. Final Verdict

1. **Does ARCHITECTURE_V3.md define the actual problem space correctly?** Directionally yes — it names project discovery, evidence merging, problem-space definition, elicitation, and readiness gating, which the live data confirms are the real problems. But it omits the truthfulness invariant its own relaxation trades against, quietly redefines the product as the compiler, treats elicitation as a fallback when the data shows it is the primary path (111/148 `problem_missing`), and lacks goal-conditioning.

2. **Does it solve the root problem or mostly reorganize symptoms?** It genuinely solves one root problem — the review unit. Collapsing 148 claim cards into ~15 story cards with one decision each is the correct fix, deterministically bounded by roster size. But on the truthfulness axis it reorganizes symptoms into a less-enforceable shape: it takes implicit credit for failures 1–3 (fixed in code before the doc existed), retires the only existing integrity enforcement (the 409 gate) without replacement, keys its render gate to a function that does not perform it, and replaces mechanical verbatim checks with LLM self-policing ("a problem the evidence cannot support is not written" is an instruction to the model doing the composing). The queue problem is solved; the slop problem is moved.

3. **Is the central object correct?** Yes. The Project Story — one per confirmed real-world entity, claims as internal inventory, evidence spans as leaves — is exactly right, and the doc is genuinely centered on it. The defect is not the object but its schema: one mutable row conflates LLM draft, gate diagnosis, human classification, and approved canon, with no `approved` state distinct from machine-assigned `resume_ready`.

4. **Would it prevent another 148-item review nightmare?** At the queue level, yes — card count is bounded by the roster (~15), and re-runs are hash-skipped. But the nightmare reappears one click deep: the specified Edit path routes through the existing per-claim UI, which for personal-knowledge-os re-exposes 28 raw claims, 26+ flag-walled. Unless the drill-down is redesigned and integrity flags get a story-level disposition, the 148 items are hidden, not gone.

5. **Would a user tolerate the review workflow?** Yes. The honest count is ~15 cards + ~7–13 typed answers + ~3 classifications ≈ 24–30 interactions — double the doc's estimate but still a single sitting of minutes, which meets the burned-out-user thesis. Tolerance is conditional on never being forced into the raw-claim drill-down and on the cards showing evidence quotes so approval is a judgment, not a leap.

6. **Does it prevent incomplete projects from entering the Master CV?** On paper yes; in reality not yet, and not as specified. The gate is enforced zero times today — `build_snapshot_content` has no P-A-R bar, an approved action-only claim renders (proven by an existing test), entity 9 renders live with a one-line bug as its only Problem — and the doc's enforcement plan is a disabled UI button plus a present-tense description of unwritten code, with no `approved` status to key on. Built as a pure gate + server-side 409 + render refusal, the design works; as written, it is a promise.

7. **Does it prevent AI slop from downstream tailoring/outreach?** Partially. Numbers are well-guarded at synthesis and tailoring (verbatim gates, hallucinated-id dropping) — but outreach bodies, the one artifact that leaves the machine, have no number gate at all; composed Problems and persisted bullets are unverifiable framing that becomes the grounding corpus for the next LLM (generated text validating generated text, two hops from evidence); and the tailoring-time gate's allowed-source set is undefined for stories — unless it resolves to cited evidence chunks, it is decorative.

8. **The single highest-leverage change?** Separate machine readiness from human approval and make the gate real: a derived readiness struct (not statuses), an explicit human `approved` review status, and the P-A-R gate enforced as code at both `POST /stories/{id}/approve` (server-side 409) and `build_snapshot_content` (render refusal) — with every downstream consumer reading only the approved-story snapshot. This one change fixes the missing-approved-status flaw, the unenforced gate, the compound-gap problem, and the tailoring ambiguity simultaneously.

9. **What must be deleted?** From the code: the per-file fallback's ability to mint CONFIRMED entities (`claim_extraction.py:427-437` + the CONFIRMED `upsert_experience`), and `tests/test_roster_service.py:334`'s assertion that the fallback works (inverted, not removed); the claims-queue-as-review-surface once story cards pass exit tests. From the doc: six of the ten statuses (keep 4 + readiness struct), the three unspecced score fields (`confidence`, `career_signal_score`, `result_strength_score`), §3.7's synthesis-time cross-entity duplicate detection (replaced by a deterministic pass), and the §6 wholesale retirement of the 409 gate (replaced by the integrity/absence split).

10. **What should not be built yet?** The LLM StorySynthesizer's prose authoring (credit-gated; last, after the human-gated card and quote display exist); `bullets_json` candidate bullets (render P/A/R directly first); persisted `questions_json` (derive from readiness; store only answers); per-job resume rendering; embedding/vector dedupe; any LLM judge in the pipeline; anything multi-user.

11. **Implement as written, modify, or reject?** **Modify.** The central reframe — Project Story as the review and render unit, claims as inventory, elicitation over invention — is correct and should be built. Required modifications: (a) split `readiness` (derived struct handling compound gaps) from `review_status` with an explicit human `approved` state, and enforce the P-A-R gate server-side and at render, in code; (b) Phase 0 first — delete the fallback's CONFIRMED minting and split integrity/absence flags, keeping integrity flags blocking; (c) replace §3.7's impossible synthesis-time duplicate detection with a deterministic cross-entity evidence-overlap pass, and add duplicate-bullet/metric checks to §5; (d) replace the claim-scoped Edit path with story-component edit-attest (`story:{id}:{component}` attestation scheme) that never surfaces raw claims or flag strings; (e) render evidence chunk quotes on the card for every component ref including composed-Problem `supporting_refs`, and restrict component refs to `claim_ids`; (f) fully specify S5 — story→`MasterCv` adapter, stable component addressing, number gate resolved against cited evidence chunks, an outreach-body number gate, pipeline empty-condition over approved stories; (g) cut the LLM self-score fields and restore the deterministic leverage ranking; (h) the heuristic synthesizer selects and gates only — never authors prose; defer bullets, derive questions; (i) build the live-shaped 15-entity fixture first and adopt the T1–T16 exit tests per phase, with the LLM synthesis run last and credit-gated; (j) validate attested answers structurally, add a story-level result-addresses-problem check or explicit P/R adjacency, and add a cross-source metric-conflict question (red-team 8) so "keeps the strongest version" stops being a pick-the-biggest-number rule.
