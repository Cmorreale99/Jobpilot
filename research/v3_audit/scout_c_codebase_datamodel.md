# Scout C — Codebase Alignment, Data Model, Master CV Semantics, Tailoring Safety

Audit of `docs/ARCHITECTURE_V3.md` (sections 11, 12, 15, 16 of the 22-section audit).
Every code citation below was read in the working tree at branch `v2/master-cv`.

## Critical flaws

- **The legacy per-file fallback not only survives — it auto-CONFIRMS entities.** `run_claim_extraction` falls back to per-file grouping (`app/services/claim_extraction.py:428-437`) and persists each group via `upsert_experience`, which stamps `ExperienceStatus.CONFIRMED` (`app/db/claim_repository.py:127-128`, `app/services/claim_repository.py:51-52`). Files become render-eligible confirmed entities with zero human roster review, directly contradicting the doc's §1 claim that "HUMAN roster confirmation" is "(V2, unchanged)" plumbing v3 can build on.
- **An approved action-only claim renders today — the §3.4 render gate exists nowhere.** `render_claim_bullet` explicitly renders "the action alone" when Result is missing (`app/domain/resume_context.py:90-99`); neither `build_snapshot_content` (`app/domain/master_cv_snapshot.py:70-105`) nor `build_resume_context` filters on completeness. `tests/test_claims_routes.py:249-279` seeds a `result_kind=MISSING` claim and asserts a successful docx — a test that proves the behavior v3 forbids.
- **The docx render path bypasses both the snapshot and the confirmed-entity filter.** `render_master_cv_artifact` snapshots, then rebuilds context from *live* repo queries (`app/services/master_cv_render.py:68-72`), and `build_resume_context` has no `ExperienceStatus` check (`app/domain/resume_context.py:117`) — a discarded entity with approved claims still renders, and the docx can diverge from the version number it is stamped with. V3 inherits this split enforcement unexamined.
- **`project_stories` conflates LLM scratchwork with approved canon in one row.** The §2 status enum mixes lifecycle (`draft`, `pending_review`), gate diagnosis (`needs_*`), human classification (`portfolio_inventory`, `exclude_low_value`), and dedupe workflow (`duplicate_needs_merge`); §3.4 says synthesis *assigns* `resume_ready` while §2's arrow chain makes `resume_ready` the post-review terminal — the §4 card even shows "resume_ready ✓" *with an unclicked Approve button*. Approved-by-human is not representable distinctly from gate-passing draft.
- **Approving a story canonizes LLM-composed problem text that nothing validates, and §2's provenance guarantee is false for it.** The composed `problem_space` appears in no file and was typed by no user; `supporting_refs` are model-asserted; the §5 checks cover only numbers (`invented_metric_count`) and ref existence (`orphan_component_count`), never semantic support. "Every rendered sentence still walks back to a file the user owns or a statement the user typed" (§2) does not hold for a composed problem.
- **"Approve story → the claims its components cite are approved" (§4) silently bypasses the flag gate and degrades the golden set.** Today a flagged claim cannot be approved as-is (`FlaggedClaimApprovalError`, `app/services/claim_review.py:47-58`; 409 at `app/api/claims.py:179-180`). Story approval batch-approves cited claims the human never individually read — the doc retires the "per-claim approve 409 gate" (§6) without saying what happens to a cited claim's `validation_flags`, and `golden_examples` (`app/domain/evaluation.py:181-223`) would record these as human approve-verdicts they are not.
- **S5 is one sentence sitting on a break that fails *silently*.** `master_cv_from_snapshot` iterates `content["sections"][*]["claims"]` (`app/domain/master_cv_snapshot.py:134-151`); a story-shaped snapshot yields `MasterCv(claims=[])`, and the pipeline then logs a warning and returns success with zero matches and zero drafts (`app/services/pipeline.py:141-153`). Ship the snapshot change without a new adapter and the nightly pipeline no-ops without error. No story→`MasterCv` adapter, no `highlight_claim_ids` successor, no number-gate source is specified.
- **The doc's own provenance is broken.** It "supersedes … `docs/REVIEW_LAYER_AUDIT.md`" — that file does not exist in the repo (`docs/` contains only `V2_AUDIT.md` and `ARCHITECTURE_V3.md`), and the load-bearing corpus numbers (148 pending claims, 12 entities, "~7 questions") are unverifiable from the repository. [auditor: two corrections — (1) `docs/` also contains `adr/` (empty) and `research/MODEL_EVAL_PLAN.md`; `REVIEW_LAYER_AUDIT.md` is indeed absent from the entire tracked tree and exists only on branch `docs/review-layer-audit` (commit 2375ba9). (2) The corpus numbers ARE verifiable against the live `jobpilot.db` sitting untracked at the repo root: 148 pending claims and the one existing rejection confirmed — but confirmed entities number **15** (12 claim-bearing), so the doc's "~12" undercounts its own roster.]

## 11. Current Codebase Alignment

### 11.1 Already supports v3

- **Roster layer (the story's entity boundary):** `app/domain/roster.py` (proposer/assigner protocols, `HeuristicRosterProposer`, `HeuristicChunkAssigner`), `app/services/roster.py` (`run_roster_detection`, `run_roster_assignment`), `app/api/roster.py` (confirm/discard/merge/rename), `app/llm/roster.py` (DEEP proposer, BULK assigner), migration `0010_roster_layer.py`, `web/components/roster.tsx`. §1's "one story per confirmed entity" maps 1:1 onto `Experience(kind, status, aliases)` (`app/domain/claims.py:230-255`).
- **Claims-as-inventory:** the extraction path (`app/services/claim_extraction.py`) already lands everything as `pending_review` and never auto-approves (`_to_storable`, lines 183-204); `extraction_hash` skip (`claim_extraction.py:457-462`, migration `0011`) is exactly the economics §2 wants for `synthesis_hash`.
- **Attestation machinery:** `SOURCE_USER_ATTESTATION` evidence rows + `plan_claim_edit` (`app/domain/claims.py:1008-1090`) — the doc's §3.1 "existing machinery" for typed answers. (But see §12: it is *claim*-scoped; `source_ref = claim:{id}:{field}` at `claims.py:998-1005` — no story-scoped scheme exists.)
- **Grounding/verbatim plumbing:** `verbatim_in` (`app/domain/par_validation.py:82-89`) shared by validator and the LLM extractor's grounding filter (`app/llm/extraction.py:225-268`, `_quote_ok` line 315); the cached-context batching pattern (`llm/extraction.py:189-217`) is the template §3's one-DEEP-call-per-entity synthesis needs.

### 11.2 Contradicts v3 / must be retired or rebuilt

- **One claim = one review card:** `GET /claims/queue` serializes each pending claim as a card (`app/api/claims.py:159-169`, `_serialize_claim` 96-133); `web/components/claims.tsx:166-264` maps claims to cards with per-claim approve/reject/attest. §4 replaces this with ~12 story cards; the doc says the claim UI "retires" (§6) — the entire component and the three decision routes (`app/api/claims.py:172-213`) are the retirement surface. §S4 says "claim drill-down retained inside the card" — no current code supports a claim view nested under an entity; `_serialize_claim` doesn't even include the experience name (the web component joins it client-side, `claims.tsx:121-122`).
- **Flagged claim = reviewable item:** `FlaggedClaimApprovalError` (`app/services/claim_review.py:43-58`), the 409 (`api/claims.py:179-180`), and the UI's disabled approve (`claims.tsx:214-226`). V3 §6 retires the per-claim 409 gate and makes "problem-absence … story-level status, not claim noise" — but says nothing about the other flag families (`result_problem_coupling`, `outcome_quote_not_verbatim`, `DUPLICATE_OUTCOME_FLAG` from `claim_extraction.py:217-222`) on claims a story cites. Unresolved: approving a story that cites a coupling-flagged claim either violates the current invariant or requires an unspecified flag-resolution step.
- **Missing-Results queue:** `review_queue(missing_results_only=True)` (`claim_review.py:33-40`), `?missing_results=true` (`api/claims.py:159-169`), `MissingResultForm` (`claims.tsx:66-102`). Retired by §6; replaced by `needs_result` status + question. Fine — but the *resolution* path (`ClaimEdits.result_kind` guardrails, `claims.py:1021-1029`) has no story-level equivalent specified: what `result_kind`/`result_status` does an answered story-question stamp on which claim?
- **Master CV generated from claims directly:** `SNAPSHOT_KIND = "approved_claims"` and `build_snapshot_content(experiences, claims)` (`app/domain/master_cv_snapshot.py:35, 70-105`); `create_master_cv_snapshot` queries `status=APPROVED` (`app/services/master_cv_snapshot.py:23-30`); `render_master_cv_artifact` re-queries approved claims for the context (`app/services/master_cv_render.py:70-72`); `_claim_entry` is the content unit (`master_cv_snapshot.py:43-67`). What must change for "render unit: story": a new snapshot builder keyed on `resume_ready` stories, a new content shape (breaking `snapshot_of`), `build_resume_context` consuming `bullets_json` instead of `render_claim_bullet`, `master_cv_render.py` querying stories, and `master_cv_from_snapshot` replaced (see §16). The frozen renderer contract itself (`bullets: [str]`, `resume_context.py:1-21`) can survive untouched — the one part genuinely "unchanged."
- **Legacy one-file-one-experience path:** still present and reachable — `gather_drive_groups`/`gather_github_groups` (`claim_extraction.py:101-180`) seed one `ExperienceSeed` per Drive doc/repo, invoked as the fallback at `claim_extraction.py:434-437`; `app/tools/run_claim_extraction.py:41-44` documents the fallback as expected behavior. Worse than "legacy": every Drive doc lands `section=PROFESSIONAL_EXPERIENCE` (`claim_extraction.py:115-117`) and `upsert_experience` creates the row **CONFIRMED** (`db/claim_repository.py:127-128`) — the fallback manufactures confirmed, render-eligible, professional-experience entities from filenames with no human in the loop. V3 must delete this path, not tolerate it "loudly logged"; the doc never mentions it.
- **GitHub repo = resume-ready project — what is the bar today?** Two answers: (a) fallback mode — none; the repo is auto-confirmed at extraction time (`claim_extraction.py:456` + confirmed upsert). (b) roster mode — one human confirm click (`api/roster.py:124-127`), after which **a single approved action-only claim** puts the repo on the resume (`build_snapshot_content` requires only CONFIRMED + ≥1 approved claim, `master_cv_snapshot.py:89-104`). There is no credible-Problem/Result bar anywhere today. §3.4 is the fix *if* it is enforced at the snapshot builder as promised — the doc's "enforced three times" is currently enforced zero times.
- **Incomplete PAR can still render: YES.** Evidence: `render_claim_bullet` (`resume_context.py:90-99`) — "A missing Result simply renders as the action alone"; no completeness filter in `build_snapshot_content` (`master_cv_snapshot.py:80-105`) or `build_resume_context` (`resume_context.py:102-143`); proven by `tests/test_claims_routes.py:249-279` (renders a docx from a `result_kind=MISSING` claim) and by `_seed_claim`'s default `MISSING` kind (`test_claims_routes.py:56`).
- **Raw extracted entity becomes user-facing content:** in fallback mode, yes (above). In roster mode, raw LLM proposals surface directly as roster cards (by design, one-click cost — `llm/roster.py:13-16`), and raw extracted P/A/R text is the review card body (by design in V2). V3 *adds* raw LLM output as user-facing content in two new places — the synthesized story card body and `questions_json` — with only the human gate behind them; the doc should say so explicitly instead of implying only claims were ever raw.

**JSON blobs vs relational rows — what breaks.** For ~12 stories, blobs are defensible for *rendering*. They structurally break: (1) **per-component approval state** — there is no component identity to transition; §4's component edit-attest has nothing to address (contrast `claim_evidence.field` giving every claim link a queryable field, `models.py:274-292`); (2) **component-level provenance queries** — the review card's evidence quotes + click-through URLs are built by joining `claim_evidence` → `evidence` (`api/claims.py:96-112`, `evidence_source_url` `claims.py:893-918`); `evidence_refs` buried in `actions_json` require reparsing every blob and cannot be indexed or integrity-checked by the DB; a deleted/merged evidence row leaves silent dangling refs that only the `orphan_component_count` runtime check can find; (3) **the golden set** — `golden_examples` (`evaluation.py:181-223`) exports labeled claim rows; story decisions inside blobs produce no per-component labels, and the §4 cascade stamps approve-labels on claims the human never read, so the one dataset V2 was explicitly accumulating ("decisions are the V3 golden-set data", CLAUDE.md) degrades in exactly the release named after it. A workable compromise the doc doesn't state: components may **only** cite `claim_ids` (never bare `evidence_ids`), making claims the relational provenance/approval substrate and the JSON purely presentational — but §3.2's "`evidence_refs` (claim/evidence ids)" explicitly allows bare evidence refs, which forfeits that.

**Can the schema support one project appearing once?** `experience_id UNIQUE` handles the happy path. It does not handle: the story row of an entity that later becomes `merged` (row persists, doc silent); re-synthesis of the merge *target* (its `synthesis_hash` changes because claims/evidence moved — good — but if the target's story was approved, see the ApprovedProjectStory hole); or two confirmed entities that synthesis flags `duplicate_needs_merge` where one is already approved (merge moves claims out from under an approved story's `component_refs`).

## 15. Master CV Semantics

**Does the doc define Master CV as structured approved data?** Yes, cleanly at the headline level: §1 "Master CV = snapshot of resume_ready stories", §4 "Approve story → story becomes canonical", §2's provenance chain bullet → component → claim/evidence → chunk → source. Approved stories are the canonical durable object *in intent*. In *schema* they are a status value on a mutable draft row (see §12), which undercuts "durable."

**Are bullets downstream renderings, not source of truth?** **No — and this is a quiet regression from V2.** Today bullets are derived deterministically at render time from approved claim fields (`render_claim_bullet`, `resume_context.py:90-99` — "no rewriting, no invention"). V3 §2/§3.5 *persists* LLM-composed `bullets_json` in the story row, generated at synthesis, approved wholesale with the story, and (per §S5) selected directly by tailoring. Persisted generated prose inside the canonical object is source-of-truth in every way that matters. V2's render layer was mechanically incapable of rewording; V3's is prompt-constrained only, with the number gate as the sole mechanical check on bullet content (§S1 does apply it at synthesis validation — good — but wording, emphasis, and causality claims in bullets are checked by nothing).

**Can different resumes be generated from the same approved stories?** Plausible and implied (§S5 "tailoring selects among approved stories/bullets by job fit"), and the frozen renderer contract (`bullets: [str]`) supports arbitrary story subsets mechanically. But no per-job render path, artifact kind, or selection persistence is specified — `artifacts` today is `master_cv_docx` only (`models.py:295-313`), and `TailoredMaterials` produces text fields, not a docx. "Different resumes from the same stories" is currently an aspiration with no landing zone.

**Is there ANY path where generated prose becomes canonical evidence?** Three, in increasing severity:

1. **The composed Problem.** After approval, the synthesized `problem_space` lives in `project_stories.problem_space` as render canon. It was never a claim, never faced the PAR problem gate (`_validate_problem` requires a declared cost dimension/inefficiency — `par_validation.py:157-174`; story problems have `problem_status` but no such requirement), never faced `verbatim_in` (deliberate §3.1 relaxation), and after approval is validated by **nothing** — §5's checks are numbers and ref-existence only; "a problem the evidence cannot support is not written" is a prompt instruction dressed as an invariant. And §2's guarantee that "every rendered sentence still walks back to a file the user owns or a statement the user typed" is **false** for a composed problem: the sentence exists in no file and was typed by no user; what walks back is a model-selected set of `supporting_refs`.
2. **The §4 approval cascade.** "The claims its components cite are approved" converts a story-level judgment into claim-level canon. The human approved a composed summary *of* those claims, not the claims — a subtly wrong claim (e.g., one carrying a coupling flag or an inflated tool list) inherits approved status because the story that cited it read well. This also collides head-on with `FlaggedClaimApprovalError`: either the cascade violates the current invariant (`claim_review.py:47-58`) or flagged cited claims block story approval — the doc specifies neither. And the cascade's approvals enter the golden set (`evaluation.py:161-178`) as human verdicts, polluting exactly the label the doc says stays clean ("a rejection still only ever means 'false'" — true, but an *approval* stops meaning "human read this and confirmed it").
3. **Persisted bullets feeding tailoring.** Bullets are LLM output persisted in canon and then used as the grounding corpus for the next LLM (tailoring) — generated text grounding further generation, two hops from evidence. Numbers survive the chain only if the tailoring-time gate's allowed-source set is defined against evidence, not against bullet text (see §16).

**Where does the synthesized problem text live after approval and what validates it?** In `project_stories.problem_space`, and nothing — the honest answers the doc should state outright. It never becomes an evidence row (only *user-typed* answers do, §3.1), which at least prevents future claims from citing it. That containment is the one genuinely sound choice here and deserves to be stated as an invariant: *composed story text is render-only and must never be written into `evidence`.*

## 16. Tailoring and Outreach Safety

**Current mechanism (verified).** `master_cv_from_snapshot` adapts snapshot claims to `ParClaim`s with `source_ref = claim:<id>` (`domain/master_cv_snapshot.py:126-151`); `claim_ref_id` recovers the id (`domain/tailoring.py:35-41`); `highlight_claim_ids` rides in `applications.materials_json` (`tailoring.py:65-97`). The number gate `unsupported_numbers` (`tailoring.py:52-62`) is applied in `LlmMaterialsTailorer.tailor` with allowed sources = `claim_text` of the *selected* claims + the posting text, failing closed to the heuristic (`llm/drafting.py:128-139`). Hallucinated highlight ids are dropped structurally (`llm/drafting.py:107-123`).

**Two live gaps in the CURRENT gate that v3 §S5 inherits without comment:**
- **Outreach has no number gate at all.** `LlmOutreachDrafter.draft` (`llm/drafting.py:149-183`) validates only that `subject`/`body` are non-empty strings (`_parse_message`, 252-255). An invented metric in the outreach email body — the one artifact that actually leaves the machine (`services/outreach_send.py`) — is caught by nothing today. Any v3 safety claim about downstream generation must extend the gate to `run_drafting`'s outreach step (`services/outreach.py:67-69`), not just tailoring.
- **The gate checks the model's prose against *claim text*, not cited evidence.** A number verbatim in a claim's `result_text` passes even if that claim was user-attested with a typo; conversely this is fine — but under v3 the analogous choice matters enormously (below).

**Is every factual generated sentence traceable under v3?** Not specified. §S5's entirety: "tailoring selects among approved stories/bullets by job fit — highlight traceability now points at story components." No component addressing scheme (story id? component index? bullet index?), no `materials_json` schema change (today's `from_json` at `tailoring.py:88-97` silently coerces unknown shapes), and — since bullets regenerate on re-synthesis with no stable ids (§12) — any bullet-index reference dangles after the next synthesis run.

**Are unapproved / evidence_only / incomplete projects excluded?** Structurally yes **iff** tailoring reads the snapshot (which contains only resume_ready stories per §3.4's render gate) rather than the `project_stories` table. The doc's §1 pipeline line ("tailoring / outreach / prep draw from approved stories") implies but never states the snapshot-only read. `evidence_only` "unless explicitly allowed": **no allowance mechanism exists anywhere in the doc** — either delete the possibility or specify the flag; an unspecified escape hatch is how evidence-inventory ends up in a cover letter.

**Are metrics guarded — does the number gate survive the refactor?** The doc asserts numbers "remain under the V2 verbatim/number-factuality gates" (§3.3) and §S1 applies an unsupported-numbers check at *synthesis*. But the *tailoring-time* gate's allowed-source set is undefined for stories, and every candidate answer fails differently: (a) component summaries (`result_summary`, `action_summary`) — LLM prose; a number verbatim in evidence but paraphrased out of the summary false-positives, and a number invented *into* the summary at synthesis (if it slipped the synthesis gate) launders straight through; (b) bullet text — generated-text-validates-generated-text, two hops from evidence; (c) cited chunk text via `evidence_refs` → chunks — the only sound choice, requires a resolver walk the current gate doesn't do and the doc doesn't specify. Pick (c) explicitly or the gate is decorative.

**Are generated claims prevented from becoming new facts?** In V2, yes: materials live in `applications.materials_json` and nothing re-ingests them. In V3, mostly: composed story text stays out of `evidence` (§15) — but persisted `bullets_json` becomes the tailorer's selection corpus, so generated prose *is* the new grounding layer even though it never enters the evidence table. State the containment invariant and gate tailored numbers against evidence chunks, and this is acceptable; leave it implicit and it will erode.

**What precisely breaks when the render unit changes from claims to stories?**
1. `master_cv_from_snapshot` (`master_cv_snapshot.py:134-151`) finds no `"claims"` keys in a story-shaped snapshot → `MasterCv(claims=[])`.
2. `run_application_pipeline` sees `not master_cv.claims` and **returns success** with zero matches/drafts, logging one warning (`pipeline.py:141-153`). The pipeline doesn't crash — it silently stops producing anything, indefinitely, which its own idempotency guarantees will make look normal.
3. Everything downstream of the adapter assumes `ParClaim`: `select_claims`/`render_claim`/`claim_text` (`tailoring.py:106-135`), `_claims_block` (`llm/drafting.py:189-199`), `claim_ref_id`, and matching (`run_matching` takes a `MasterCv`).
4. **The v3 equivalent is not specified.** Required and absent from the doc: a `story_master_cv_from_snapshot` (or a `MasterCv` successor carrying stories/bullets with stable component refs), a `highlight_*_ids` successor with a stable addressing scheme, a `materials_json` schema version, the number-gate source definition, an outreach-body gate, and the pipeline's empty-gate condition restated over resume_ready stories. Until those exist, S5 is a caption, not a plan.
