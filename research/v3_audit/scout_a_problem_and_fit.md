## Critical flaws (top findings)

- **The story status machine has no `approved` state.** The §2 enum ends at `resume_ready | needs_* | ...`; §3.4 says synthesis itself does "status assignment"; S5 says the snapshot "takes resume_ready stories." Read literally, a machine-assigned status is the render key and an unapproved LLM draft can reach the docx. Human approval exists only in §4 prose ("story becomes canonical") with no named status or field.
- **The resume_ready gate checks co-presence, not causation.** §3.3's result shape (`result_summary`, `metric?`, `evidence_refs`, `confidence`, `result_strength_score`) has **no action linkage**, and §3.2 ranks actions by `career_signal_score`, not by problem-remediation. A story can gate with a Problem about X, Actions about Y, and a Result about Z. The 21 live `result_problem_coupling` flags have no story-level answer anywhere in the doc.
- **"Compose and elevate" (§3.1) has no verification mechanism beyond numbers.** Composed Problem statements and action summaries are LLM prose whose only checks are refs-exist (`orphan_component_count`) and verbatim numbers (`invented_metric_count`). Decorative refs — real evidence ids attached to a stretched claim — pass every named check. This is the new slop channel V3 opens while closing the old ones.
- **The Edit path is incoherent and re-exposes raw claims.** §4 Edit = "per-component drill-down (existing edit-attest flow)" — but that flow edits *claims* (`app/services/claim_review.py`, `ClaimEdits` in `app/domain/claims.py:~1012`), and a composed `problem_space` lives on the story row, **on no claim**. The specified mechanism cannot edit the component it's specified for, and it drops the user back into the internal extraction artifacts V3 exists to hide.
- **The review-time gate is a disabled UI button, not a server invariant** (§3.4: "the approve control is disabled"), while §6 explicitly **retires the per-claim 409 approve gate** (`approve_claim`, `app/services/claim_review.py:47-56` — the only thing today preventing approval of integrity-flagged claims). §4's approve-cascade then bulk-approves cited claims. Net: integrity flags (`action_tool_not_in_text` ×37, coupling ×21 live) lose their only enforcement point and gain no replacement.
- **The doc describes `build_snapshot_content` future behavior as if present.** §3.4: "at render (`build_snapshot_content` refuses any entity without a resume_ready story)". The actual function (`app/domain/master_cv_snapshot.py:70-105`) filters only claim `APPROVED` + entity `CONFIRMED` — no story gate, no P-A-R bar (the REVIEW_LAYER_AUDIT render bar was never implemented; resume.md admits "designed but not yet enforced"). Live proof: claim 373 is `approved` under `investment-decision-workflow-engine` — an entity with **zero** problem-bearing claims — and renders today. [auditor: the "zero problem-bearing claims" characterization is wrong — claim 373 itself carries a `problem_text` ("streamlit run executed dashboard.py as a top-level script…") and a problem evidence link; the entity's 8 *pending* claims are 8/0/1, but across all 9 claims it has one problem-bearing (373, the approved one). - **The legacy per-file extraction fallback survives V3 unmentioned.** `run_claim_extraction` falls back to per-file grouping whenever no confirmed roster exists (`app/services/claim_extraction.py:427-437`). V3 (§1, §6) never retires it; a fresh user or wiped roster silently rebuilds file-shaped experiences underneath the story layer — the V2 audit's root cause, still reachable.

## 1. Actual Problem Space

**Verdict: the proposed definition is directionally correct — it names the real hard problem (project discovery, evidence merging, problem-space definition, elicitation, readiness gating) and matches both audits' evidence — but it has four defects that matter for architecture.**

**(a) It quietly redefines the product as the compiler.** CLAUDE.md defines Jobpilot as the full pipeline: Master CV → matching → tailoring → outreach → interview detection → prep. The compiler is the hard *upstream* stage and the current bottleneck, not the product. Correct framing: *the evidence-to-story compiler is the load-bearing subsystem whose output every downstream stage consumes; everything downstream already exists and is comparatively easy.* The definition as written would license ignoring the downstream contracts — which is exactly the mistake ARCHITECTURE_V3 then makes (S5 never mentions matching or interview prep, which consume the same `master_cv_from_snapshot` bridge — `app/services/pipeline.py:129-132`, `app/services/interview_scan.py:141-142`).

**(b) It omits the truthfulness invariant.** "Accurate" is too weak. resume.md (commit `43d217a`) states the actual bar: *"no prose leaves the machine unless it traces to evidence a human approved"* and *"A fabricated metric in front of a hiring manager is not a bug; it is a credibility event."* The hard problem includes **verifiability under LLM composition** — every sentence must walk back to owned evidence or a typed attestation. This must be in the problem definition because V3's §3.1 relaxation ("compose and elevate") trades exactly against it.

**(c) It underweights the user's own thesis.** resume.md's business problem: the job market is an employer's market *because only one side is playing with AI*, and the real bottlenecks are **psychological — discouragement, burnout, hopelessness**. Under that thesis, "minimal user effort" is not UX polish; it is the product's core mechanism (the system does the relentless part so the human only does the judgment part). A 148-card review queue is therefore not tech debt — it is *the product failing at its thesis*: the demoralized user it exists for will abandon it (REVIEW_LAYER_AUDIT §1: "realistically it never gets done"). The definition should state a hard review budget (single sitting, minutes) as a constraint, which the doc does operationalize (§4: "~15 interactions, minutes not hours").

**(d) It misses two properties the live data proves are load-bearing:**
- **Elicitation is the primary manufacturing step, not a fallback.** 111/148 pending claims carry `problem_missing`; of the 12 claim-bearing entities, **5 cannot reach Problem+Result from evidence at all** (investment-decision-workflow-engine 0 problems, Stock Market Simulation 0 problems, AI-Recovery-navigation 0 results, Cooper.ai 0 results, personal-knowledge-os 0 results). [auditor: "0 problems" for investment-decision-workflow-engine holds for its pending queue (8/0/1) only — its one approved claim (373) carries a Problem (a one-line technical bug) and a verified Result, so "cannot reach Problem+Result from evidence at all" overstates that entity; the other four verified as stated, as is 111/148 `problem_missing`.] "Asking the user only for high-value missing information" is how *most* stories become resume-ready. The doc gives this one subsection (§3.6) and one button (§4) — the thinnest treatment of its most-used path.
- **Incrementality and decision preservation.** The corpus refreshes (nightly pipeline, new commits); the compiler must be idempotent and must never re-litigate a human decision. V2 got this right (`replace_unreviewed_claims`, fingerprint skips) and V3 inherits `synthesis_hash` (§2) — but the problem definition should require it, since it constrains every design choice (e.g., §4's "no LLM call needed" answer flow).

Also missing: **goal-conditioning.** "Highest-leverage actions" is undefined without a target audience; §3.8 correctly ranks for "target data/AI/analytics engineering roles" — the problem definition should include the target-role parameter, since "resume-ready" is relative to a market, not absolute.

**Improved definition (delta, not replacement):** Jobpilot's load-bearing subsystem is an evidence-to-career-story compiler: transform a noisy, redundant, heterogeneous personal corpus into a small set of **verifiably true**, high-leverage, project-level career stories — *conditioned on target roles* — with a review budget of minutes, not hours, because the end user is by thesis burned out. Every story sentence traces to owned evidence or a typed attestation; missing information is elicited via the fewest highest-value questions (the **primary** path to readiness for evidence-sparse projects, per live data); the compiler is incremental, idempotent, and never overrides a human decision; its approved output is the **only** input to every downstream consumer (render, tailoring, outreach, matching, prep).

## 2. Architecture Summary

**Central object:** the **Project Story** — one row per confirmed roster entity in a new `project_stories` table, `experience_id` unique ("the same project appears once", §2). Claims are demoted to internal "inventory" (§0: "Claims are inventory"); evidence and claims tables untouched (§2).

**Pipeline (§1):** sources → normalization → roster detection → human roster confirmation → chunk assignment (char spans) → claim extraction + PAR validation (all V2, unchanged) → ★ project story synthesis (new: one DEEP LLM call per confirmed entity, input = entity + assigned chunks + claim inventory, output = draft story, §3) → ★ story review (~12 cards, one decision each, §4) → Master CV = snapshot of resume_ready stories → tailoring/outreach/prep "draw from approved stories + their bullets."

**Persisted:** `project_stories` rows (status, `problem_space`+`problem_status`, `actions_json`, `results_json`, `bullets_json`, `questions_json`, `synthesis_hash`) via migration 0012 (S2); claims and evidence persist unchanged; review decisions persist (approve cascades approval onto cited claims, §4). **Temporary scratchwork: nothing.** The doc marks nothing ephemeral — even LLM drafts persist as `draft`-status rows, and the claim-extraction stage keeps running at BULK cost forever despite its output being demoted to inventory that synthesis could arguably derive from chunks directly (synthesis input already includes the chunks, §3). The doc never justifies keeping both LLM stages.

**User reviews:** story cards only (approve / edit / answer-question / classify portfolio / exclude, §4); per-claim drill-down retained inside cards (S4).

**Feeds the Master CV:** a snapshot of `resume_ready` stories, "P-A-R sections + bullets" (S5); `build_snapshot_content` is claimed to refuse entities without a resume_ready story (§3.4).

**Generates final prose:** synthesis itself writes the story paragraphs and 1–3 candidate bullets with `component_refs` (§3.5); tailoring "selects among approved stories/bullets by job fit — highlight traceability now points at story components" (S5).

**Actual architectural commitments** (concrete, testable): (1) `project_stories` table, unique per entity, replaced idempotently (§2); (2) the status enum `draft → pending_review → resume_ready | needs_problem | needs_result | needs_action | evidence_only | portfolio_inventory | duplicate_needs_merge | exclude_low_value` (§2); (3) one DEEP call per entity, `synthesis_hash` skip, prompt-cached (§3); (4) Problem composition relaxation with `supporting_refs`, else `needs_problem` + fixed question (§3.1); (5) results evidence-backed/attested only, V2 number gates retained (§3.3); (6) resume_ready gate "enforced three times": synthesis status assignment, review approve control, render refusal in `build_snapshot_content` (§3.4); (7) bullets only when resume_ready (§2); (8) minimum targeted questions from a fixed menu (§3.6); (9) entity dedupe via roster merge, `duplicate_needs_merge` from synthesis (§3.7); (10) ranking orders queue and CV (§3.8); (11) approve-cascade approves cited claims, uncited stay inventory; answer attests + re-gates with **no LLM call**; exclude terminal (§4); (12) `eval_stories` → `validation_runs` kind `story_eval` with `invented_metric_count`=0 and `orphan_component_count`=0 (§5); (13) retires: Missing-Results queue, per-claim 409 approve gate, 148-card UI, `shelved` status (§6); (14) S1–S6 build order, exit tests in S6 (§7); (15) migration: 148 pending claims become inventory, no re-extraction, decided claims untouched, claim-queue UI removed after cards ship (§8).

**Ambiguities and silences (each is a finding):**
1. **No `approved` story status** — §2's machine vs §3.4's "at synthesis (status assignment)" vs §4's "becomes canonical" conflict; the render key (`resume_ready`, S5) may be machine-assigned. (Critical; see flaws list.)
2. **`evidence_only` is never defined** — it appears once, in the §2 enum, and never again [auditor: minor — the phrase "Evidence-only / portfolio inventory projects" also appears in §5's run-report list (item 4); the status is still never defined and has no §4 control, so the finding stands]; its difference from `portfolio_inventory` and `exclude_low_value` (which do get §4 buttons) is unstated. `needs_action` likewise has no elicitation question in §3.6's menu — an unreachable-by-review status.

4. **The "Answer & re-ready" flow's terminal state** — after an answer re-passes the gate, does the story auto-approve or wait for an explicit approve? §4 says only "synthesis re-evaluates the gate locally."
5. **The `MasterCv` bridge** — `master_cv_from_snapshot` (`app/domain/master_cv_snapshot.py:126-151`) parses the *claims*-shaped snapshot and feeds matching, tailoring, and interview prep (`pipeline.py:129-132`, `interview_scan.py:141-142`). 6. **Whether tailoring may reach non-resume_ready inventory** — §4 says portfolio/excluded entities "never render"; *render*-scoped wording; tailoring is not addressed (and REVIEW_LAYER_AUDIT §2 explicitly wanted unchosen claims "re-selectable" for tailoring — a temptation V3 neither forbids nor allows).

9. **What the approve-cascade means for provenance** — the composed `problem_space` exists on no claim, so "the claims its components cite are approved" (§4) covers Actions/Results but leaves the Problem's canonical provenance implicitly on the story row; nothing states how an *evidenced* (composed) problem is later audited.

## 4. Core Object Review

**What the core object should be:** the **Approved Project Story** — one per real-world entity, carrying a Problem Space, remedy Actions, caused Results, and readiness status — with **evidence spans** as the immutable ground-truth leaves and **claims** as internal, never-user-facing intermediates. Document is wrong (it's a container, the V2 root-cause). Evidence span is wrong as *core* (it's the leaf). Atomic claim / PAR triplet are wrong (extraction granularity ≠ decision granularity — proven by 148 cards / 12 entities). Master CV entry is wrong (it's a derived render). Project capsule ≈ project story; the story with an approval state is the correct canonical unit.

**Is ARCHITECTURE_V3.md centered on it?** Yes: `project_stories` one-per-entity with unique `experience_id` (§2); "V3's task is to construct one coherent Project Story per project" (§0).

**Are claims internal candidates?** Yes by declaration — "Claims are inventory" (§0), "feeding inventory, not the queue" (§6), uncited claims "simply stay inventory" (§6).

**Does one project appear exactly once?** Yes, structurally (§2 unique FK) plus §3.7's merge path for roster-level dupes. Caveat: enforcement of *entity* uniqueness is the human's roster review; synthesis-side duplicate detection is best-effort LLM (§3.7) with no exit test (S6).

**Does the user review Project Stories rather than raw claims?** Yes for the primary flow (§4).

**Critical failure — internal extraction artifacts still reach the user:** the **Edit** decision is specified as "per-component drill-down (existing edit-attest flow)" (§4) and S4 retains "claim drill-down ... inside the card." The existing edit-attest flow is per-*claim* machinery (`app/services/claim_review.py`; `ClaimEdits`/edit-plan in `app/domain/claims.py:~1012-1080`). Two consequences: (a) any wording fix routes the user through raw claims — the exact artifact class V3's §0 promises the user never sees; (b) **the mechanism cannot do its job**: a composed `problem_space` exists on the story row and on no claim, so claim-level edit-attest has nothing to edit — editing the story's most important component requires new story-component edit machinery that the doc hand-waves as "existing machinery" (§4: "all over existing machinery"). This is a specification hole at the core object's write path. The fix is obvious and should be stated: component-level edit-attest on the story (typed text → `user_attestation` evidence row linked to the *component*), with claims never surfaced except as optional provenance views.

## 5. Project Story Model Audit

**Does every project require a defined Problem Space?** Yes for *resume-readiness* (§3.4), with honest downgrade (`needs_problem`, §3.1) — good. But a project can hold `portfolio_inventory`/`evidence_only` status with no problem forever, which is correct behavior; the defect is that those statuses' semantics are undefined (§2 lists them; `evidence_only` never reappears).

**Are Actions selected as remedies to the Problem — is selection COUPLED?** **Half-coupled, and decoupled exactly where the live data needs coupling most.** §3.2's first line couples selection ("Select the strongest Actions that remedied the Problem Space"), but: (a) the *ranking* criterion is `career_signal_score` — an independent axis; (b) for the 5+ live entities with **no** problem space, "remedied the Problem Space" is vacuous — the doc never defines action selection under `needs_problem`, so in practice actions are chosen by career signal alone for the plurality of real projects; (c) when the user later attests a problem, §4 explicitly re-gates "**no LLM call needed**" — so actions are **never re-selected against the newly attested problem**. The one-shot coupling only ever operates on the minority of entities whose evidence already stated a problem. The desired model's P→A arrow is prompt guidance, not architecture.

**Are Results tied to those Actions?** **No — structurally absent.** §0 defines Results as "outcomes **caused by those actions**", but §3.3's component shape has no action reference and §3.4's gate requires only co-presence "all under the same `experience_id`". The A→R causal arrow exists nowhere in the data model. V2 at least had the (weak) `resolves` coupling per claim; V3's story layer drops even that without replacement. The 21 live `result_problem_coupling` flags are the empirical form of this failure and the doc never mentions them.

**Missing Problem → targeted question, never invented?** Yes (§3.1) — with the caveat that "compose and elevate" moves the invented/composed boundary into LLM judgment with no deterministic backstop (see §3 row 7 and Critical flaws).

**Missing Result → same?** Yes (§3.3: `needs_result` + fixed question; numbers stay under V2 verbatim gates).

**Technical GitHub projects without business context downgraded?** Yes — `needs_problem`/`evidence_only`/`portfolio_inventory` all exist in the §2 enum and §4 gives Portfolio/Exclude controls. Undefined: who/what assigns `evidence_only` vs `portfolio_inventory`, and `needs_action` has no elicitation question in §3.6 (unreachable-by-review status).

**Low-value projects excluded from rendering?** Yes — `exclude_low_value` terminal (§4: "excluded is terminal like roster discard") plus the render gate (§3.4). Tailoring-side exclusion unstated (see §6 below).

## 6. Resume-Ready Gate

**Is the gate explicit?** Yes — §3.4: `resume_ready` only with one evidenced/user-attested Problem Space + ≥1 approved Action + one evidenced/user-attested Result, same `experience_id`. Wording defect: "approved Actions" is undefined — actions carry no individual approval state in the §2 schema (approval is story-level), so at synthesis time the gate can only mean "≥1 action with non-empty `evidence_refs`". The doc should say so.

**Enforceable in code?** Yes, if built as: (1) a pure gate function in S1's `ProjectStory` domain model (analogous to `validate_claim` in `app/domain/par_validation.py`); (2) a **server-side** check in `POST /stories/{id}/approve` (S4) that 409s a non-passing story — the doc promises only "the approve control is disabled" (§3.4), a client-side control, while §6 *retires* the existing per-claim 409 gate (`approve_claim`, `app/services/claim_review.py:47-56`). A UI-disabled button is not an invariant; one curl bypasses it; (3) the rewritten `build_snapshot_content` (S5).

**Applied before Master CV generation?** Promised (§3.4: render refusal in `build_snapshot_content`) — **but the doc states it in the present tense about a function that does not do it.** The current implementation (`app/domain/master_cv_snapshot.py:70-105`) filters claims by `APPROVED` (line 80) and entities by `CONFIRMED` (line 90) and nothing else: no story concept, no P-A-R completeness.
